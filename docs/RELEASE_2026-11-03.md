# Release 2026-11-03: putting today's changes live

How to release what was merged to `main` on 3 November 2026. The release itself is one command, `deploy.sh`
([deploy/README.md §6](../deploy/README.md#6-releasing-an-update)). This page adds what to check before and after, the till setup the
printing change needs, and how to roll back.

Allow **30 minutes**, outside AQUA HUB's opening hours. The API is down for a few seconds during step 3.

## 3. Release

Connect to the server as `deploy`, then write down what is live now, in case you need to roll back:

```bash
ssh deploy@<server>
cd /home/deploy/ultimatepos
git -C backend log -1 --oneline     # note this commit
git -C frontend log -1 --oneline    # and this one
df -h /                             # at least ~5 GB free for the images and the backup
```

Optional: see which migration the live database is on. It should be `20261027112110_BusinessEtimsEnabled`, the newest in the repo.

```bash
cd /home/deploy/ultimatepos/backend/deploy
./pos.sh exec -T db sh -c 'psql -U "$POSTGRES_USER" "$POSTGRES_DB" -tc "select max(\"MigrationId\") from \"__EFMigrationsHistory\""'
```

If it shows an older one, the migrate step will apply the ones in between: they come from earlier releases, and step 1 of the
release backs up first. Read their names in the migrate output.

Then release:

```bash
/home/deploy/ultimatepos/backend/deploy/deploy.sh
```

| Step it prints | What happens | Expect |
|---|---|---|
| 1/5 Backing up the database | `backup.sh`: a dump in `/home/deploy/ultimatepos/backups`, copied off the server if `BACKUP_REMOTE` is set | "dumped … to …". **Note the file name** |
| 2/5 Pulling the latest main | backend, frontend and website, fast-forward only | Stops if the server copy has local changes: see §6 |
| 3/5 Building the images | api, web, site one at a time | 5–10 minutes |
| 4/5 Updating the database | the `migrate` container | "Applying 0 migration(s): none" |
| 5/5 Restarting | `up -d`: the API restarts (seconds of downtime) | "Released. https://… is up." |

## 5. AQUA HUB's till: receipt printing

The till prints through Chrome to the **Xprinter XP-T80A** (USB, installed in Windows as a printer). There is no cash drawer. Do this
once on the till after the release.

1. **Windows:** XP-T80A installed with the Xprinter driver and set as the **default printer**. Its paper size is 80 mm (driver
   default).
2. **Choose the print settings once, by hand.** Open Chrome with the till profile (step 3's shortcut **without**
   `--kiosk-printing`), sign in, make a sale, click **Print**. In Chrome's print dialog choose XP-T80A, **Margins: Default**,
   **Scale: 100**, **Headers and footers: off**, and print. Chrome remembers these in that profile.
3. **Silent printing shortcut.** A desktop shortcut whose target is:

   ```text
   "C:\Program Files\Google\Chrome\Application\chrome.exe" --kiosk-printing --user-data-dir="%LOCALAPPDATA%\UltimatePOS-Till" https://<your POS address>/pos
   ```

   Close every Chrome window first, then start the till from this shortcut. It always uses that profile, so the settings from step 2
   apply and no print dialog opens.
4. **In the app: Settings → Point of sale** on the till: **Receipt paper: 80 mm thermal**. Switch **Print receipt automatically**
   on only if they want it. It is per device, so it changes only this till.
5. **Test:** a sale of 1 item and one of many items (20+ lines). Each prints once, complete, on one strip; the right edge is not cut;
   the paper does not run on far past "Thank you". If the right edge is cut, tell us: the receipt width goes from 72 mm to 70 mm.

Auto-print waits for KRA's signature only where eTIMS is on. AQUA HUB has eTIMS off, so its receipts print as soon as the sale
completes.

## 6. If something goes wrong

| Symptom | Do |
|---|---|
| Step 2 stops: "Not possible to fast-forward" or local changes | Someone edited files on the server. `git -C /home/deploy/ultimatepos/backend status` to see them; keep what is needed elsewhere, then `git -C … checkout -- .` and run `deploy.sh` again |
| Step 3 fails (out of memory) | Free memory and retry; the swap file must be on (README §2). The live stack is untouched until step 5 |
| Step 4 fails | The API was not restarted: the old version is still serving. Read the migrate output and stop; ask before retrying |
| "did not answer … within a minute" | `./pos.sh logs --tail 200 api`. If it does not recover, roll back (§7) |
| Receipts still cut off | Make sure the till runs the new frontend (hard refresh, Ctrl+F5) and §5 is done |

## 7. Rolling back

There is no database change in this release, so rolling back is code only (README §6):

```bash
cd /home/deploy/ultimatepos
git -C backend checkout <backend commit noted in §3>
git -C frontend checkout <frontend commit noted in §3>
cd backend/deploy
./pos.sh build api && ./pos.sh build web
./pos.sh up -d
```

Afterwards, put both back on `main` (`git -C backend checkout main`, same for frontend) before the next `deploy.sh`, or its
`pull --ff-only` fails on a detached checkout.

The step 1 backup is only needed if data went wrong, which this release cannot cause by itself.
